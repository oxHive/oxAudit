# Local AWS Cost Audit CLI Plan

## Goal

Build a local Go-based CLI that audits AWS costs by collecting data through the AWS CLI, storing raw evidence, normalizing data into SQLite, generating deterministic cost findings, and exporting LLM-readable summaries.

The tool is intended to run locally from an operator workstation, not in CI.

## Core Design

The audit pipeline should follow this flow:

Raw AWS CLI JSON → SQLite normalized database → deterministic findings → optional semantic index → LLM-ready exports

The main design principle is:

- Raw AWS CLI JSON is immutable evidence.
- SQLite is the canonical processed audit store.
- Findings are deterministic and reproducible.
- Markdown and JSONL exports are optimized for LLM reading.
- sqlite-vec is optional and should be added after the core relational pipeline works.

## Local Runtime Assumptions

The local machine should have:

- AWS CLI installed and authenticated.
- A local AWS profile with billing, Cost Explorer, Organizations, and read-only inventory permissions.
- Go installed for building and running the CLI.
- SQLite support through the Go application.
- Optional sqlite-vec support if semantic search is desired.
- Optional embedding provider credentials if embeddings are enabled.

The tool should not require CI, remote runners, or hosted infrastructure.

## CLI Commands

The CLI should expose these local commands:

- init
- collect
- ingest
- analyze
- embed
- export
- retrieve
- all

### init

Creates the local audit directory structure and initializes the SQLite database schema.

Responsibilities:

- Create output folders.
- Create the SQLite database.
- Apply migrations.
- Write or validate local config.
- Initialize audit metadata.

### collect

Runs AWS CLI commands locally and saves raw JSON output.

Responsibilities:

- Use the configured AWS profile.
- Collect Cost Explorer data.
- Collect account and region metadata.
- Collect resource inventory by region.
- Collect recommendations.
- Collect budget and anomaly data.
- Save every raw response to disk.
- Log command status, stderr, runtime, and output file path.
- Continue past optional command failures when appropriate.

### ingest

Reads saved raw JSON files and loads normalized records into SQLite.

Responsibilities:

- Parse Cost Explorer output.
- Parse AWS Organizations account data.
- Parse EC2, EBS, EIP, NAT Gateway, ELB, RDS, Lambda, CloudWatch, and S3 inventory.
- Parse Compute Optimizer and Cost Explorer recommendations.
- Insert normalized rows into relational tables.
- Store source file references for traceability.

### analyze

Runs deterministic finding rules against the SQLite database.

Responsibilities:

- Detect waste.
- Detect underutilized resources.
- Detect tagging gaps.
- Detect unexpected spend spikes.
- Detect commitment utilization issues.
- Generate findings with evidence, savings estimates, confidence, risk, and recommended action.
- Link findings to resources and source files.

### embed

Optional command that creates semantic embeddings for findings.

Responsibilities:

- Read current findings.
- Generate compact text for each finding.
- Store embeddings in sqlite-vec or a related local vector table.
- Maintain mapping between embeddings and finding IDs.
- Avoid becoming the source of truth; embeddings are only for retrieval.

### export

Generates local LLM-friendly and human-friendly output files.

Responsibilities:

- Export findings as JSONL.
- Export findings as Markdown.
- Export findings as CSV.
- Export an LLM digest.
- Export a remediation backlog.
- Export summary reports by service, account, priority, and category.

### retrieve

Optional local retrieval command for querying findings.

Responsibilities:

- Accept a natural-language query.
- Apply SQL filters.
- Optionally apply keyword search.
- Optionally apply sqlite-vec semantic search.
- Return compact, relevant finding context.
- Support local LLM workflows.

### all

Runs the full local pipeline in order:

- init
- collect
- ingest
- analyze
- embed, if enabled
- export

## Analysis Rule Engine

The analyzer should use deterministic rules.

Each rule should:

- Have an ID.
- Have a name.
- Query normalized data.
- Generate zero or more findings.
- Include evidence.
- Estimate savings where possible.
- Assign priority.
- Assign confidence.
- Assign risk.
- Suggest a concrete action.
- Link back to resources and source files.

## Core Rules

### Unattached EBS Volumes

Detect EBS volumes with state indicating they are available or unattached.

Finding should include:

- Volume ID.
- Region.
- Size.
- Volume type.
- IOPS.
- Age.
- Tags.
- Estimated monthly storage cost.
- Recommended snapshot and delete action.

Priority should increase with size, age, and provisioned IOPS.

### Old EBS Snapshots

Detect snapshots older than the configured retention threshold.

Finding should include:

- Snapshot ID.
- Source volume ID.
- Snapshot age.
- Volume size.
- Description.
- Tags.
- Recommended retention validation and deletion action.

Risk should depend on tags, retention policy, and whether the snapshot appears manually created.

### Unassociated Elastic IPs

Detect Elastic IPs without an active association.

Finding should include:

- Allocation ID.
- Public IP.
- Region.
- Tags.
- Recommended release action.

This is usually high-confidence low-risk waste if ownership checks pass.

### Stopped EC2 Instances

Detect EC2 instances stopped longer than the configured threshold.

Finding should include:

- Instance ID.
- Instance type.
- Stopped age if available.
- Attached storage implications.
- Tags.
- Recommended termination or archival workflow.

Savings should focus on attached resources, not stopped compute.

### Underutilized EC2 Instances

Use Compute Optimizer recommendations when available.

Finding should include:

- Instance ID.
- Current instance type.
- Recommended instance type.
- Estimated monthly savings.
- Performance risk.
- Recommended validation step.

These findings usually require engineering validation.

### Overprovisioned EBS Volumes

Use Compute Optimizer recommendations or local heuristics.

Finding should include:

- Volume ID.
- Current type and size.
- Recommended configuration.
- Estimated savings.
- Risk and validation guidance.

### Idle Load Balancers

Detect load balancers with little or no traffic when metrics are available.

Finding should include:

- Load balancer ARN.
- Type.
- Region.
- Age.
- Traffic evidence.
- Recommended deletion or consolidation action.

### NAT Gateway Cost Issues

Detect high NAT Gateway spend through Cost Explorer and resource inventory.

Finding should include:

- Service cost.
- Region.
- Account.
- NAT Gateway IDs if available.
- Usage type evidence.
- Possible architectural causes.
- Recommended VPC endpoints or route review.

These findings may have medium confidence unless traffic attribution is strong.

### High CloudWatch Logs Cost

Detect high CloudWatch Logs ingestion or storage cost.

Finding should include:

- Service cost.
- Log groups where available.
- Retention settings.
- Stored bytes.
- Recommended retention and log volume review.

### Missing Required Tags

Detect resources missing required ownership or cost allocation tags.

Finding should include:

- Resource ID.
- Resource type.
- Missing tag keys.
- Account.
- Region.
- Recommended tagging action.

This is governance-oriented and may not have direct savings.

### Untagged Spend

Detect Cost Explorer spend that is not allocated to expected tags.

Finding should include:

- Tag key.
- Untagged amount.
- Service.
- Account.
- Period.
- Recommended tag activation and enforcement action.

### Savings Plans Underutilization

Detect low Savings Plans utilization.

Finding should include:

- Utilization percentage.
- Net unused commitment.
- Period.
- Recommended review of commitment scope and workload changes.

### Reserved Instance Underutilization

Detect low RI utilization.

Finding should include:

- Utilization percentage.
- Unused hours or cost.
- Service.
- Account or region if available.
- Recommended modification, exchange, or planning action.

### Low Commitment Coverage

Detect high On-Demand usage for steady-state compute.

Finding should include:

- Service.
- Account.
- Region.
- On-Demand spend.
- Existing coverage.
- Recommended Savings Plans or RI evaluation.

### Cost Anomalies

Detect and import AWS cost anomalies.

Finding should include:

- Anomaly date.
- Service.
- Account.
- Region if available.
- Cost impact.
- Root cause if available.
- Recommended investigation action.

### Unexpected Region Spend

Detect spend or resources in regions that are not expected.

Finding should include:

- Region.
- Account.
- Services.
- Cost.
- Resources if available.
- Recommended ownership and compliance review.

## Finding Priority Model

Use deterministic priority assignment.

### P0

Urgent issues.

Examples:

- Active unexpected spend spike.
- Large unexplained anomaly.
- Potential runaway resource.
- Possible abuse-related spend.
- High-cost unexpected region or service.

### P1

High-confidence waste or large savings.

Examples:

- Large unattached EBS volumes.
- Large unassociated Elastic IP footprint.
- Old expensive snapshots.
- Obvious idle infrastructure.
- High savings with low remediation risk.

### P2

Optimization requiring validation.

Examples:

- Rightsizing recommendations.
- Commitment coverage recommendations.
- NAT architecture changes.
- RDS downsizing.
- CloudWatch ingestion reduction.

### P3

Governance or low-savings cleanup.

Examples:

- Missing tags.
- Low-dollar stale resources.
- Budget gaps.
- Alerting gaps.
- Documentation issues.

## Confidence Model

Use simple confidence values:

- High.
- Medium.
- Low.

### High Confidence

Use when evidence is direct and remediation is straightforward.

Examples:

- EBS volume state is available.
- Elastic IP has no association.
- Required tags are absent.
- Snapshot is older than threshold.

### Medium Confidence

Use when evidence is strong but context is needed.

Examples:

- NAT Gateway architecture appears inefficient.
- CloudWatch Logs spend is high.
- Load balancer appears idle based on limited metrics.

### Low Confidence

Use when more data is required.

Examples:

- Spend increase without clear resource attribution.
- Rightsizing without utilization data.
- Unknown owner or unclear business purpose.

## Risk Model

Use simple risk values:

- Low.
- Medium.
- High.

### Low Risk

Examples:

- Tagging fixes.
- Releasing clearly unassociated resources after owner confirmation.
- Applying log retention.
- Deleting unattached resources after snapshot and approval.

### Medium Risk

Examples:

- Rightsizing instances.
- Reducing provisioned IOPS.
- Changing NAT architecture.
- Modifying storage lifecycle rules.

### High Risk

Examples:

- Production database changes.
- Deleting snapshots without retention validation.
- Major network routing changes.
- Commitment purchases.

## Savings Estimation

Savings should be marked as estimated unless directly derived from billing data.

Recommended approach:

- Use Cost Explorer for service, account, region, and usage-level realized cost.
- Use static configurable pricing tables for simple resource estimates.
- Use Compute Optimizer savings where available.
- Use AWS Pricing data in a later version if needed.
- Prefer conservative savings estimates.
- Store savings as monthly estimated USD.

For stopped EC2, do not claim compute savings if the instance is already stopped. Estimate savings from attached EBS, EIPs, snapshots, and related infrastructure.

- How confident the tool is.
- What the risk is.
- What action is recommended.

## Local Retrieval Plan

The retrieve command should support local question answering over findings.

Recommended retrieval order:

- Apply SQL filters.
- Apply keyword search if available.
- Apply sqlite-vec semantic search if enabled.
- Merge results.
- Sort by relevance, priority, and savings.
- Return compact context.

Example local retrieval use cases:

- What can we safely clean up this week?
- What are the biggest EC2 savings?
- Which findings need app team validation?
- What is causing network-related cost?
- Which accounts have the most waste?

## sqlite-vec Use

sqlite-vec should be optional.

Use it for semantic search over findings and evidence.

Do not use it for:

- Source of truth.
- Cost aggregation.
- Deterministic analysis.
- Final savings calculations.

## Error Handling

The local CLI should be resilient.

Recommended behavior:

- Required collection failures should fail the run.
- Optional regional service failures should be logged and skipped.
- Permission errors should be clearly reported.
- Empty AWS responses should not be treated as failures.
- Partial runs should preserve already collected raw files.
- The user should be able to rerun only failed stages.

## Idempotency

The tool should support reruns.

Recommended behavior:

- Each audit run gets a unique audit run ID.
- Raw files are associated with a specific run.
- Ingestion should be repeatable.
- Analysis should use deterministic finding IDs.
- Exports should be overwritten for the current run.
- Historical runs may remain in SQLite for comparison.

## Audit Run ID

The audit run ID should be deterministic or semi-deterministic.

Recommended format:

- timestamp

- audit_run table.

## Local Performance

The tool should be efficient enough for a workstation.

Recommended choices:

- Stream AWS CLI stdout to files.
- Use transactions for SQLite inserts.
- Batch inserts where practical.
- Avoid loading huge raw files into memory when not needed.
- Run regional collection with limited concurrency.
- Make concurrency configurable.
- Avoid concurrent writes to SQLite unless carefully managed.
- Prefer one writer transaction per ingestion stage.

## Concurrency

Use conservative local concurrency.

Recommended model:

- Cost Explorer commands run sequentially or with low concurrency.
- Regional inventory collection can run concurrently.
- Limit region concurrency to a small number.
- Ingestion writes should generally be serialized.
- Analysis can run sequentially for simpler debugging.

## Security

Local security considerations:

- Do not store AWS credentials in the audit output.
- Do not print secrets.
- Treat raw AWS inventory as sensitive.
- Avoid committing the audit output directory to source control.
- Add a generated .gitignore if useful.
- Scrub or flag sensitive tags if needed.
- Keep embeddings local if sensitive resource metadata cannot be sent to an external API.

## Final Architecture Summary

The local Go CLI should behave as a deterministic cost-audit pipeline:

- The AWS CLI collects evidence.
- Raw JSON is saved locally.
- SQLite stores normalized audit data.
- Rules generate explainable findings.
- Exports produce LLM-friendly context.
- sqlite-vec optionally improves semantic retrieval.

The most important outputs are:

- db/aws_cost_audit.sqlite
- exports/findings.jsonl
- exports/llm-digest.md
- exports/remediation-backlog.md

The best source of truth is SQLite.

The best LLM input is the generated digest plus JSONL findings.
